# Fatia 1 (Base) — Plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Colocar no ar, no Railway, o esqueleto do sistema real da ECLAK com login individual, 5 perfis, menu por perfil, Admin › Usuários, Admin › Parâmetros versionados, Fornecedores e auditoria, sobre Supabase.

**Architecture:** Next.js 16 fullstack em repositório novo. Server Actions validam com Zod, checam perfil e gravam auditoria; o banco (Postgres do Supabase) é acessado só pelo servidor via Drizzle; Supabase Auth cuida da sessão por cookie. Regras puras (dinheiro, permissões, esquema de parâmetros) ficam em `src/domain/` sem I/O.

**Tech Stack:** Next.js 16.4.x, React 19.3, Tailwind v4, TypeScript estrito, Supabase (Postgres, Auth, Storage) + Supabase CLI local, Drizzle ORM + drizzle-kit, `postgres` (driver), `@supabase/ssr`, `@supabase/supabase-js`, Zod, Vitest, Railway.

**Spec:** `docs/superpowers/specs/2026-11-18-backend-sistema-real-design.md` (no repositório `eclak-mockup`). Protótipo de referência visual e de regras: repositório `eclak-mockup` (branch `main`).

## Global Constraints

- Repositório novo (nome sugerido `eclak-sistema`); o protótipo não é alterado.
- Um único ambiente no Railway (produção) e um único projeto Supabase. Migrações testadas no Postgres local (Supabase CLI) antes de rodar em produção. Seed fictício só local.
- Dinheiro em `bigint` **centavos**; percentuais em `numeric(6,3)`; datas de negócio `date`; eventos `timestamptz`; "hoje" no fuso `America/Cuiaba`; IDs `uuid`.
- RLS ligado em todas as tabelas de `public`, sem políticas para `anon`/`authenticated`.
- Toda action que altera valor, status, perfil ou regra grava em `auditoria` (quem, quando, tabela, id, antes, depois).
- Cadastros com exclusão lógica (`excluido_em`); nada é apagado fisicamente.
- Perfis: `diretor`, `consultor`, `operacional`, `fin_operacional`, `fin_estrategico`. Filiais: `Rondonópolis`, `RS`.
- Camada estratégica (imposto, rateio, margem final): `diretor`, `fin_operacional`, `fin_estrategico`.
- Cadastro de usuário só pelo Diretor; sem auto-cadastro.
- Marca: azul #2E5C71 dominante, laranja #F26531 só em destaque, texto #333132, sem preto puro, sem vermelho, sem gradiente, sem ícone de estrelinha para IA, sem tag "Fase 2". Textos de interface em português-BR.
- Layout desktop 1440–1920 px, igual ao protótipo.

## Review Focus

1. **Usuário desativado com sessão aberta** — deve perder acesso na próxima requisição, não só no próximo login. Teste em Task 4.
2. **Valor monetário digitado no formato brasileiro** ("1.234,56", "R$ 3.500", "20725,93") — deve virar centavos exatos, e entrada inválida deve ser recusada com mensagem, nunca gravada como 0 ou NaN. Teste em Task 3.
3. **Consultor chamando a action de Parâmetros ou Usuários diretamente** (sem passar pela tela) — deve ser recusado no servidor. Teste em Tasks 6 e 7.
4. **Dois diretores salvando Parâmetros ao mesmo tempo** — nenhuma versão pode ser perdida nem sobrescrita; cada save cria versão nova e a vigente é a de `vigente_desde` mais recente. Teste em Task 7.
5. **Diretor rebaixando o próprio perfil ou desativando a si mesmo** quando é o único Diretor ativo — deve ser recusado (o sistema ficaria sem administrador). Teste em Task 6.
